# anchored-evidence-gate

[![License: Apache-2.0](https://img.shields.io/badge/License-Apache_2.0-blue.svg)](./LICENSE)

**把"模型说它匹配"变成"模型必须证明它匹配"。**

这是一个**零依赖、纯函数**的小库，抽取自开源导诊项目
[诊途（hospital-guide）](https://github.com/yuan293/hospital-guide) 的核心安全机制。
它解决一个很具体的问题：

> 当你把模型的输出用 schema `enum` 约束在一个**受控词表**内时，模型仍可能
> **把 A 的证据配给 B 的词**（语义错配）。这种错配在医疗、客服、工单路由等场景里代价很高。

本库提供两个可独立复用的把关函数——它们让这类错配**结构性不可表达**，
而不是依赖事后拦截或提示词禁令。

---

## 为什么需要它

约束输出到词表（`enum`）能防止模型"自由发挥"，但**防不住"张冠李戴"**：

| 模型输出 | 词表词 | 证据 | 问题 |
| --- | --- | --- | --- |
| {"keyword": "鼻塞", "evidence": "鼻子老是出血"} | 鼻塞 | 鼻子老是出血 | 科室碰巧对，但**记录的症状是错的**，而出血是需要警惕的征象 |
| {"keyword": "腹痛", "evidence": "肾疼"} | 腹痛 | 肾疼 | 跨器官错配 |
| {"keyword": "心悸", "evidence": "浑身不得劲"} | 心悸 | 浑身不得劲 | 笼统感受被当作具体症状 |

在「诊途」的真实评测里，这三类错配都**真实出现过**。本库的核验规则让它们在
结构上**根本无法通过**。

---

## 安装 / 使用

本库零依赖，可直接复制 `src/` 使用，或作为子模块引入。在 Node（≥18，仅需 ESM）中：

```js
import {
  evidenceMatchesKeyword,
  isShortEvidenceFragment,
  acceptPolish,
  REFERENCE_SYNONYMS,
} from './packages/anchored-evidence-gate/index.js';
```

> 本项目刻意保持**零第三方运行时依赖**（`dependencies: {}`），
> 便于在受限环境（内网、离线、供应链敏感场景）中直接审计与复用。

## API 一：`evidenceMatchesKeyword(keyword, evidence, synonyms?)`

判定证据片段是否支持某个词表词。**四条接受规则**，满足其一即通过：

| # | 规则 | 说明 | 例子 |
| --- | --- | --- | --- |
| ① | **字面** | 证据包含词表词本身 | 词`咳嗽` ← `咳嗽三天` |
| ② | **形态锚点** | `X疼`/`X痛` 词：词干在证据中且证据含「疼/痛」；`X出血` 词：词干在证据中且含「血」 | 词`腰痛` ← `腰部疼痛`；词`鼻出血` ← `鼻子老是出血` |
| ③ | **双语素同现** | 二字词的两字都出现在证据中 | 词`血尿` ← `尿里带血` ✅；词`耳鸣` ← `耳朵疼` ❌（缺「鸣」） |
| ④ | **登记同义形** | 命中你登记的口语核心词（可附"须同时出现某词"约束） | 词`腹痛` ← `肚子疼` |

```js
evidenceMatchesKeyword('腰痛', '腰部疼痛');              // true（规则②）
evidenceMatchesKeyword('耳鸣', '耳朵疼');                // false（缺「鸣」）
evidenceMatchesKeyword('腹痛', '肚子疼', REFERENCE_SYNONYMS); // true（规则④）
evidenceMatchesKeyword('鼻塞', '鼻子老是出血', REFERENCE_SYNONYMS); // false ← 结构性拒绝
```

### 登记同义表（`synonyms`）

格式为 `{ 词表词: [[核心词, 可选的正则约束], ...] }`：

```js
const synonyms = {
  腹痛: [['肚子', /疼|痛/]],   // 必须同时出现「肚子」和「疼/痛」
  发热: [['发烧']],             // 出现「发烧」即算命中
};
```

**登记原则**：给出的核心词必须是该口语**独有**、且**不能反推出别的症状**。
`REFERENCE_SYNONYMS` 导出了「诊途」累积的 43 组中文口语映射，可直接用或作为范例。

## API 二：`acceptPolish(parsed, opts?)`

当模型被允许**改写面向用户的问句措辞**时，用这个 **fail-closed** 把关保证它
"改不出危险内容"。合格返回 `{title, description}`，否则返回 `null`
（**由调用方回退到配置原文**——模型改坏了只是文案不好看，不影响业务）。

它一票否决：

- **诊断性结论**：`诊断`、`确诊`、`一定是`…
- **用药建议**：`开药`、`用药`、`处方`、`药量`…
- **淡化风险**：`不必就医`、`无需就医`、`不用担心`…
- **被改成陈述句**：必须仍含疑问特征（`？`、`是否`、`有没有`…）
- **长度越界**

```js
acceptPolish({ title: '肚子不舒服时，排尿是否有异常？' }); // ✅ 采纳
acceptPolish({ title: '你是否已经确诊为胃炎？' });          // ❌ 诊断性措辞
acceptPolish({ title: '这不用担心，是否继续？' });          // ❌ 淡化风险
acceptPolish({ title: '你的肚子疼是肠胃问题' });            // ❌ 陈述句
```

可通过 `opts` 覆盖默认词表：`{ maxLen, minLen, forbidden, questionish, maxDescriptionLen }`。

## API 三：`isShortEvidenceFragment(evidence, chief, opts?)`

强制证据必须是**主诉原文中的短连续片段**（默认 2–8 字），
防止模型引用整句来"凑"通过核验。

```js
isShortEvidenceFragment('咳嗽三天', '我咳嗽三天了有点发烧');   // true
isShortEvidenceFragment('我咳嗽三天了有点发烧', '我咳嗽三天了有点发烧'); // false（整句）
```

## 可迁移场景

这套机制与具体业务解耦，核心问题是通用的"**受约束生成 + 证据可核验**"：

- **症状标准化 / 分诊**（本库来源场景）
- **意图分类**：把用户话术映射到受控意图枚举，并要求给出原文依据
- **工单路由**：映射到受控工单类型，证据必须来自工单原文
- **标签抽取 / 合规审核**：受控标签 + 可追溯证据
- **任何"模型输出进枚举、且需要可核验依据"的流程**

---

## 设计取舍（诚实说明）

- **保守优先**：核验不通过就剔除该证据（进而可能走向"转人工/弃权"）。
  这会让意译型表达（如"耳朵嗡嗡响"→`耳鸣`）被拒——需要**事后再登记同义形**补回。
  这是刻意的：**宁可多转人工，也不放行可疑结论。**
- **规则是枚举上限**：本库只能判定"证据是否支持词表内的词"，
  无法处理"词表里根本没有的概念"。词表外的表达仍需走兜底路径。
- **不含模型调用**：本库只做**核验**，不负责调用模型。调用、提示词、schema 由你决定。
