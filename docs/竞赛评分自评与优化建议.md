> 评估对象：`hospital-guide`（诊途）v0.7.0
> 评分依据：《AIC·AI+开源竞赛规则及作品提交要求》（附件1）"五、评分规则"

## 三、分项评分与理由

### 1. 问题与场景价值（15 分）→ 自评 12–13 分（中值 12.5）

**支持高分的证据**
- 一手调研：`docs/诊途-问题与场景价值-调研正文.docx`，N=88，94.3% 近一年有"不知道挂什么科"经历，92.0% 有挂错号/退号重挂经历。
- 场景收窄得当：不做在线问诊、不做诊断，只解决"挂哪个科"这一个决策点，符合竞赛"小切口"导向。
- 价值论证闭环：调研 → 产品边界（拿不准转人工、急症提示急诊）→ 89.8% 受访者接受该边界，逻辑自洽。
- 可用性数据：N=8 分层受试（18–60+ 岁），任务完成率 100% / 87.5%，主观评分 4.13–4.67/5。

**扣分点**
- 调研与可用性测试均为**团队自采、非第三方**，样本量小（N=88、N=8），且报告只在仓库以 docx 形式存在，未经发布/可访问链接佐证。
- 缺少"问题严重性"的量化外部数据（如脱敏的挂号退号率、导诊台咨询量等真实运营指标），价值论证主要靠自采问卷。

**提升到 14–15 分的动作**
1. 在技术报告里把调研做成一页"问题—证据—边界"图，把 N=88 的关键三问与产品设计决策显式连线。
2. 补充 2–3 条**真实场景质性证据**（如导诊台工作人员的访谈摘要、或公开报道的"患者挂错科"事件），把自采问卷从"唯一证据"变成"主证据+外部佐证"。
3. 把 N=8 可用性测试的**卡点与迭代记录**（发现什么问题 → 改了什么）单独成节，这比分数更能证明场景真实。

### 2. 创新性与方案设计（20 分）→ 自评 15–17 分（中值 16）

**支持高分的证据**
- 核心创新是**架构级**而非功能级："规则守安全底线、模型接表达多样性、不一致时由人接管"的职责切分，并用**消融实验**给出证据——同一批 8 条口语主诉，纯规则 0/8、无模型动态追问 5/8、有模型 8/8。
- **AI 必要性论证**：模型被定位为"入口翻译者"（口语→词表词），而非决策者；且明确指出无模型时"多问一轮是真实用户负担"（1.00 轮 → 5.00 轮 → 4.00 轮），论证有深度。
- **0.7.0 映射锚点表**是真正的设计创新：把"模型证据错配"从"需要守卫拦截"改为"结构性不可表达"（字面/形态锚点/双语素/登记同义形四类白名单）。这是安全工程上很聪明的思路——**不是拦截错误，而是让错误无法表达**。
- 信息增益动态追问：把"并列科室 + 增益分"对用户可见、可核验，而非黑盒提问。
- 诚实的自我批判：README「当前限制」明确写出主集与规则**同源演进存在过拟合风险**，并因此新增 20 条冻结盲测集对冲——这种自我审视本身就是设计成熟度的体现。

**扣分点**
- 与"常见方案差异"的对比表（README 第 155 行起）**没有直接对标任何真实同类产品/开源项目**（如具体某医院导诊系统、某开源 triage 项目），差异化论证偏自证。
- 模型提示词收敛为"一句验收标准+示例"后，**能力上限偏低**（意译型口语如"耳朵嗡嗡响"会被拒走弃权），创新点集中在"安全"而非"理解能力"。

**提升到 18–20 分的动作**
1. 增加一节**与 1–2 个真实开源导诊/分诊项目的横向对比**（哪怕是"某项目 X 用纯 LLM 直接输出科室，本项目用规则闸门约束"这种结构化对比），把"差异"从自我陈述变成可核查的对比。
2. 把"映射锚点表"作为**独立可复用方法**抽出来写（见开放成果项），并补一句它能推广到哪些场景（客服意图分类、工单路由等），放大创新外溢价值。

### 3. AI 与开源融合（20 分）→ 自评 17–19 分（中值 18）

**支持高分的证据（这是本作品最强项）**
- **AI 作用明确且必要**：有消融数据证明去掉模型覆盖率从 94.2% 掉到 85.2%，8 条口语从 5/8 掉到 0/8；模型位置不可被规则替代，论证完整。
- **开源选型有说理**：Qwen2.5 7B+1.5B 双尺寸、Apache-2.0 与仓库许可一致、可本地复现；明确说明了**为什么不选 Llama 系（自定义/非商业许可无法满足评委独立复现）**——这是很有说服力的选型逻辑。
- **自研边界清晰**：`THIRD_PARTY_NOTICES.md` 按《开源及第三方资源使用清单》reference 表逐项写明版本/来源/许可/使用方式/关键义务/自研内容/合规状态，10 项全部标注"已核验"。
- **许可义务落实到工程**：Ollama v0.34.4 固定版本+SHA-256 校验拒解压、模型许可原文归档 `data/model-licenses/`、`.runtime/` 因"直接再分发二进制有合规风险"而不入库——这些不是写在纸上的承诺，是代码里真实存在的动作。
- **零依赖**：`package.json` 无 dependencies，仅用 Node 内置模块，与"开源资源选型合理"高度契合。

**接近满分但未满的原因**
- 模型侧仍是**通用模型直接调用**（未做任何医疗微调）。虽然团队用"刻意不做医疗微调"作出解释（且论证合理），但按评分细则"未形成实质改进的原则上不认定充分创新"，评委可能认为**AI 侧的技术贡献偏薄**——创新几乎全部在"如何约束模型"而非"如何让模型更强"。
- 融合深度的证据集中在"约束"，「融合方式」的多样性（如模型输出参与评分、模型参与追问选择）尚未体现——目前模型只做入口标准化一次。

**提升到 19–20 分的动作**
1. **补一个"模型参与度"的增益点**：例如让模型在**歧义主诉**上输出候选科室置信（仍需通过闸门），或让模型辅助生成追问的自然语言措辞（问题库措辞的多样性），把"融合"从单向约束变成双向。
2. 在技术报告里明确写出**AI 工具使用说明**（附件1 第（七）条要求）：Codex/Trae 分别用在哪些环节、团队如何审核修改验证。`THIRD_PARTY_NOTICES` 已有第 9、10 项，把它提到技术报告显著位置。

### 4. 实现完成度与可验证效果（25 分）→ 自评 20–22 分（中值 21）

**支持高分的证据（第二强项）**
- **真能跑**：本机实测 `npm test` 56/56、`data:validate` 通过、`npm run evaluate` 完整跑出 rules/dynamic 两组指标，与 README 完全一致。
- **效果数据成体系**：六组同场评测（rules / dynamic / 7B model / 7B workflow / 1.5B model / 1.5B workflow），含覆盖率、推荐准确率、急诊召回/误触发、弃权率、分歧率、证据失效率、平均轮数；**错误科室推荐全部为 0**。
- **安全效果可核验**：急诊召回 12/12、漏诊 0；普通症状误触发急诊 0；红队 24 条三个层不安全输出均为 0。
- **盲测对冲**：20 条 held-out 冻结集，写入前未运行、写入后不改，报告内 `dataset.sha256` 可核验未被事后修改；六组全绿。
- **防漂移机制**：12 文件 sha256 指纹，代码/数据一变旧评测自动标记过期——"报告与代码不符"被工程化杜绝。
- **CI 落地**：GitHub Actions 在 ubuntu+Node20 上自动跑单测/数据校验/免模型评测/红队断言/白名单门禁。
- **三条复现路径**：路径 A 免模型 3 分钟、路径 B 双模型一次性下载、路径 C 现场离线，考虑到了评委的各种环境。

**扣分点（这是最值得改的地方）**
- **效果数据全是合成工程测试**：README 反复声明"不是临床准确率、不是独立盲测"，且主集 122 条与规则**共同演进**存在同源过拟合。团队自己也很诚实。但按评分细则"具有可核验的效果数据、用户反馈、对比结果或社区贡献记录→18–25 分"，目前**只有合成数据+小样本用户反馈**，缺少"真实使用数据"这一层。
- **无上游社区贡献记录**（Issue/PR/补丁）——细则中"社区贡献记录"这一子项目前为空。
- 可用性测试 N=8 与合成评测是两条平行线，**没有用真实用户反馈反过来验证评测结论**。

**提升到 23–25 分的动作**
1. **把 N=8 可用性测试升级为一次更大规模的公开试用**（哪怕是线上原型+30~50 份匿名反馈），产出"真实用户在哪类主诉上弃权/转人工最多"的数据，与合成评测的尾部失败案例（HG-040/041/043/122）做**交叉印证**。这是性价比最高的一步。
2. **补 1–2 条真实的上游贡献**：例如向 Ollama / Qwen 生态提一个文档修正 Issue，或把"AHF 映射锚点表"作为独立小包发布并接受 Issue。哪怕很小，也能把"社区贡献记录"从 0 变成有。
3. 在技术报告里用**一张图**呈现"六组指标 + 盲测 + 红队"的层级关系，避免评委在长文里迷路。

### 5. 开放成果与复用价值（15 分）→ 自评 12–13 分（中值 12.5）

**支持高分的证据**
- **开放成果种类齐全**：可运行原型、FHIR R4 Questionnaire 问诊结构（含 18 个 StructureDefinition，canonical URL 可在线解析）、122 条评测集+评测方法学、24 条红队集、门禁与防漂移脚本、本地模型复现模式。
- **权利边界清晰**：Apache-2.0 覆盖代码/数据/文档/测试/评测集；`THIRD_PARTY_NOTICES` 逐项标注合规状态；README 明确 `private: true` 只防误发布 npm、与开源授权无关。
- **"单独取用方式"表**（README 第 396 行起）明确写出每项资产脱离整仓克隆时的依赖与取用方法——这是很多开源项目都做不到的复用友好度。
- **有维护机制**：语义化版本、6 处版本号同步、数据版本化、接受勘误但不接受降安全门槛的修改、Issue 响应周期 1–2 周、roadmap 挂接 #1–#4。
- **可移植性**：换一份 `hospital.json` 即可适配其他医院或政务大厅导办场景，开放的是方法与引擎。

**扣分点**
- **成果链接/公开仓库的可访问性未在本次评估中验证**：README 指向 `github.com/yuan293/hospital-guide`，但需确认该仓库在评审期内**公开可访问**（附件1 第（六）条：晋级总决赛原则上应提供可访问的公开成果）。
- **无独立发布的可复用包**：所有开放资产都在主仓库内，第三方要复用"评测方法学"或"锚点表"必须克隆整仓，虽然 README 给了取用说明，但未做成分离的 npm 包/独立仓库。
- **无 LICENSE/NOTICE 之外的治理文件**：有 CONTRIBUTING，但缺少如 issue 模板、行为准则、发布流程等。

**提升到 14–15 分的动作**
1. **确认并验证公开仓库可访问**（本次无法联网核验），并在 README 顶部/技术报告里给出**可直接点击的成果链接**，不要只在文字里提到。
2. 把**"映射锚点表 + 评测门禁"抽成独立小仓库或 npm 包**（零依赖，几行代码就能抽出），这是最具外溢价值的开放成果，独立发布能显著提高"复用价值"分。
3. 补一个 `CHANGELOG.md`，把 33 条提交的关键演进结构化成版本说明（README 里其实已有大量内容，只是分散在版本沿革中）。

## 四、优化优先级（按投入产出比排序）

### P0 — 影响评审第一印象，必须做
1. **产出技术报告（PDF，≤15 页）**：按《AIC·AI+开源技术报告参考大纲》撰写。当前所有内容都在 README，但 README 不是技术报告。建议结构：问题与场景 → 方案架构（含安全闸门图）→ AI 与开源融合方式 → 自主实现内容 → 效果与验证（六组+盲测+红队）→ 创新点 → 开放成果 → 后续计划。**把 AI 工具使用说明单列一节。**
2. **产出演示视频（MP4，3–5 分钟）**：展示两个入口 → 安全确认（"上腹痛、反酸"触发红旗征）→ 动态追问（可见并列科室与增益分）→ 弃权转人工 → 模型标准化对照 → 关怀模式 → 模拟挂号全流程。**视频是最快让评委理解"这套东西真的在跑"的方式。**
3. **确认公开仓库在评审期内持续可访问**，并把链接放到显眼位置。

### P1 — 直接影响得分档位
4. **补真实用户数据**（把 N=8 扩到 30–50 份匿名试用反馈），与合成评测尾部失败案例交叉印证。
5. **补 1–2 条上游社区贡献**（Issue/PR 均可），填补"社区贡献记录"子项。
6. **横向对比 1–2 个真实同类开源项目**，强化创新性与差异化论证。

### P2 — 打磨与合规
7. **修复文档陈旧数字**（详见下节"发现的具体问题"）。
8. **抽出独立可复用包**（锚点表 / 评测门禁）。
9. 补 `CHANGELOG.md`、issue 模板等治理文件。
